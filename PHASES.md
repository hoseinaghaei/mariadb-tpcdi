# Working on this project

For teammates and for coding agents. It says what each phase is, what counts as
finished, and which files you are expected to produce.

Read `report/00-what-we-have-to-do.md` for what TPC-DI is, and
`report/01-steps-and-validation.md` for why the plan is shaped this way. This
file is the working contract.

---

## The rules

**1. Everything runs in Docker.** No MariaDB, no JDK, no pip install on the
host. The examiner is expected to have Docker and nothing else. If you find
yourself writing "first install …", stop.

**2. Python, not shell.** The professor may be on Windows. Standard library
only — no `pip install`, ever. There were six bash scripts here once; they were
deleted for this reason.

**3. Nothing is destroyed without asking.** Any operation that replaces data
prints what is already there, asks, and accepts `--force` or `--keep` instead.
A non-interactive shell with neither flag is an error, not a guess. Use
`common.may_replace()`.

**4. A check that cannot fail is decoration.** Before you commit a verifier,
break something on purpose and watch it fail. Two checks in this repo passed
against deliberately corrupted input before being fixed; both are described in
the phase reports. Write down the negative test you ran.

**5. Verifiers do not mutate.** Three of TPC's four appendix queries `INSERT`.
Run them through `common.run_appendix()`, which wraps writers in a transaction
and rolls back. `verify_phase_03` asserts `DImessages` is unchanged afterwards.

**6. Compare against the source, not against a literal.** `DimDate` has 25,933
rows because `Date.txt` has 25,933 lines — read the file and compare. A number
typed into a check stops meaning anything at a scale factor nobody has run.

**7. The spec is the authority.** Cite clause numbers. `reference/qasim-mysql/`
is a third-party MySQL implementation kept as a cross-check; its own README
says it does not pass the audit, so it generates hypotheses, never answers.

**8. Never soften the audit.** `tools/appendices/` is read-only and pristine.
MariaDB adaptations are generated by `scripts/adapt-appendix.py` so the diff
against the original is always available. If a test fails, fix the ETL.

**9. Say what is measured and what is assumed.** Every phase report ends with
what is still unverified. If you inferred something, label it an inference
until you have measured it.

## The module contract

One module per phase: `tpcdi/phaseNN_shortname.py`, holding **both** how the
phase loads and how it is checked. A check belongs beside the code it tests.

```python
"""Phase N -- one line. Plan step N. Report: report/phases/phase-NN-name.md"""
NUMBER = 5
TITLE = "broker dimension"              # shown by verify_di.py
DESCRIPTION = "load DimBroker from HR.csv"   # shown by benchmark_di.py

def run(scale, force=False, keep=False):
    """Do the work. Raise common.Fail with a message a human can act on."""

def verify(scale, c):
    """Add checks to the tally with c.want(condition, message, detail)."""
```

Then add it to `PHASES` in `tpcdi/__init__.py`. Both entry points pick it up.

Everything shared — Docker, MariaDB, prompting, the check tally, appendix
execution — is in `tpcdi/common.py`. Add to it rather than duplicating.

### Running it

```
python benchmark_di.py --scale 5              every phase, in order
python benchmark_di.py --scale 5 --phase 5    one phase
python verify_di.py    --scale 5              every check
python verify_di.py    --scale 5 --phase 5    one phase's checks
```

`--force` replaces without asking, `--keep` never replaces. SF=5 is the
correctness scale factor (Clause 8.1.3); SF=3 is the small one for quick loops.

### What a finished phase leaves behind

| | |
|---|---|
| `tpcdi/phaseNN_*.py` | `run()` and `verify()` |
| `sql/di/NN_*.sql` | the SQL, if the phase has any, with clause references in comments |
| `report/phases/phase-NN-*.md` | the report, structure below |
| a line in `tpcdi/__init__.py` | the registry |
| a commit | explaining what was learned, not just what was added |

### The report structure

Follow `report/phases/phase-04-reference-data.md`. Sections:

1. **Goal** — and why this phase is in this position
2. **Where the inputs come from** — a table of file, clause, what it gives
3. **How it runs** — the command
4. **Results** — the numbers, at both scale factors
5. **Validations** — a table of check, result, and the command that proves it
6. **Defects found** — in the data, the tooling, or your own work. Include the
   ones you caused; they are the most useful part
7. **What this settles for later work**
8. **Reproducing this** — exact commands

## The phases

Phases 1–4 are done. Each entry below says what finishes it.

### Phase 1 — Obtain and inventory the TPC tools — DONE

Download `TPC-DI_Tools_v1.1.0.zip` from tpc.org and record what is in it.

**Done when** `tools/MANIFEST.md` exists with the SHA-256 and a file listing.

**What we found:** the package is DIGen and PDGF and *no SQL at all*. The four
appendix files the spec refers to are not published by TPC; they were recovered
from public repositories and verified — see `tools/appendices/PROVENANCE.md`.
The comparison tool and expected result data are not obtainable anywhere, so
there is no row-level diff against TPC's output. The audit query is the oracle.

### Phase 2 — Generate the source data — DONE

`tpcdi/phase02_generate.py`, `docker/digen/Dockerfile`.

**Done when** `digen_report.txt` carries an `End Time` and three non-zero batch
counts, and all 17 checks pass.

**Traps already handled:** DIGen runs only on Java 8; it cannot start on Linux
without a `pdgf` symlink; it exits 0 after failing, so success is judged from
the report; and PDGF needs stdin held open or its flood guard aborts the run.

### Phase 3 — The warehouse schema — DONE

`tpcdi/phase03_schema.py`, `sql/di/01_schema.sql`.

**Done when** the 20 tables of Clause 3.2 exist and TPC's appendix queries run
against them. 15 checks.

The real check is not reading our own DDL back: it is that *TPC's* SQL executes
against our tables, which proves the column names agree.

### Phase 4 — Audit and reference tables — DONE

`tpcdi/phase04_reference.py`, `sql/di/02_load_reference.sql`.

**Done when** `Audit` matches the CSVs row for row and the six reference tables
match their files line for line. 19 checks.

**Traps already handled:** every source line ends CRLF; booleans arrive as
`true`/`false` though Clause 2.2.1 says `"0"`/`"1"`; `Audit.DValue` does not fit
the type Clause 3.2.19 gives it.

### Phase 5 — DimBroker from HR.csv — NEXT

**Goal.** The smallest real transformation: read `HR.csv`, keep the brokers,
assign surrogate keys, write `DImessages`. It exercises the whole pipeline
shape at a size you can read by eye.

**Sources.** Clause 4.5.2 (the rules), Clause 2.2.2.10 (the file), Clause
3.2.2 (the target), Clause 4.4.1 (history-tracking dimensions).

**Create.** `tpcdi/phase05_broker.py`, `sql/di/03_dimbroker.sql`,
`report/phases/phase-05-dimbroker.md`.

**Rules that bite.** Only `EmployeeJobCode = 314` is a broker; everything else
is ignored (4.5.2.1). `HR.csv` fields in order are EmployeeID, ManagerID,
EmployeeFirstName, EmployeeLastName, EmployeeMI, EmployeeJobCode,
EmployeeBranch, EmployeeOffice, EmployeePhone. Every row gets `IsCurrent = 1`,
`EffectiveDate` = the earliest date in `DimDate`, `EndDate = 9999-12-31`
(4.4.1.2), `BatchID = 1`.

**Done when**
- `DimBroker` row count equals `Audit.HR_BROKERS` — 7,144 at SF=5, 4,293 at SF=3
- every `SK_BrokerID` is distinct
- every row has `IsCurrent = 1` and `EndDate = 9999-12-31`
- the audit query's six `DimBroker` tests all report OK
- the total OK count has risen from the 114 of 166 baseline

### Phase 6 — FINWIRE: DimCompany, DimSecurity, Financial

**Goal.** Parse 203 quarterly fixed-width files with three record layouts
interleaved, and build the first genuinely slowly-changing dimensions.

**Sources.** Clause 2.2.2.8 (field widths), Clauses 4.5.3, 4.5.6, 4.5.14.

**Create.** `tpcdi/phase06_finwire.py`, `sql/di/04_finwire.sql`,
`report/phases/phase-06-finwire.md`.

**Rules that bite.** The record type is three characters starting at **column
16** — `CMP`, `SEC`, `FIN`. No separators; text padded right, numbers padded
left. Process in posting-timestamp order, because SCD-2 effective dating
depends on it. `DimSecurity.SK_CompanyID` must resolve to the `DimCompany` row
*current at that date*, not the latest one (Table 4.3).

**Done when**
- every record classifies; none falls through the three types
- the daily-grain invariant holds: at most one row per natural key per day
  (4.4.1.5) — `group by CompanyID, EffectiveDate having count(*) > 1` returns
  nothing
- SCD-2 chains are intact: exactly one `IsCurrent = 1` per natural key, each
  `EndDate` equal to the successor's `EffectiveDate`, no gaps, no overlaps
- row counts and sums match the `Audit` entries for `DimCompany`,
  `DimSecurity` and `Financial`
- the audit query's 13 + 13 + 6 tests for those tables report OK

### Phase 7 — CustomerMgmt.xml: DimCustomer, DimAccount

**Goal.** Replay a hierarchical transaction stream to derive historical state.

**Sources.** Clause 2.2.2.5 (the schema), Clauses 4.5.1 and 4.5.4.

**Create.** `tpcdi/phase07_customer.py`, `sql/di/05_customer_account.sql`,
`report/phases/phase-07-customer.md`.

**Rules that bite.** Actions must be replayed in document order: NEW, ADDACCT,
UPDACCT, UPDCUST, CLOSEACCT, INACT. Parse the XML in Python with
`xml.etree.ElementTree` into a staging table, then transform in SQL — do not
try to do it in SQL, and do not pull rows into Python one at a time.

**The likely bug:** joining `DimAccount.SK_CustomerID` to the *current*
customer row rather than the one current at the account's effective date. A
foreign key will not catch it. Write a query that does.

**Done when**
- the counts match `Audit`: `C_NEW`, `C_UPDCUST`, `C_INACT`, `CA_ADDACCT`,
  `CA_UPDACCT`, `CA_CLOSEACCT`
- the data-quality alerts match: `C_DOB_TO` (10 at SF=5), `C_DOB_TY` (16),
  `C_TIER_INV` (380). These are deliberately broken records and the ETL must
  write `DImessages` alerts with the exact text Clause 4 prescribes. Loading
  them silently is a failure
- the same SCD-2 invariants as Phase 6
- the audit's 23 `DimCustomer` and 15 `DimAccount` tests report OK

### Phase 8 — The fact tables

**Goal.** `DimTrade`, `FactCashBalances`, `FactHoldings`, `FactWatches`, in the
dependency order of Table 4.3.

**Sources.** Clauses 4.5.9 to 4.5.12, and `DimTrade` at 4.5.8 / 3.2.7.1.

**Create.** `tpcdi/phase08_facts.py`, `sql/di/06_facts.sql`,
`report/phases/phase-08-facts.md`.

**Rules that bite.** `DimTrade` is *not* history-tracking — it is updated in
place. `FactCashBalances` is a running total, so compare the **sums** in
`Audit`, not only the counts.

**Done when** every surrogate key in Table 4.3 resolves, counts and sums match
`Audit`, and the audit's 14 + 4 + 8 + 6 tests report OK.

### Phase 9 — FactMarketHistory

**Goal.** The expensive one. Per security per day: 52-week high and low plus
the **earliest date** each occurred, P/E from the trailing four quarters of
FINWIRE EPS, and yield from the dividend.

**Sources.** Clause 4.5.11.

**Create.** `tpcdi/phase09_market_history.py`, `sql/di/07_market_history.sql`,
`report/phases/phase-09-market-history.md`.

**Rules that bite.** The spec warns twice that a security's surrogate key may
change inside the lookback window, so the window cannot be grouped on
`SK_SecurityID`. Use a window function; a self-join over ~2.4M rows per scale
factor will not finish. Where a company has no earnings, `PERatio` is NULL
**and** a `DImessages` alert is required with `MessageSource =
'FactMarketHistory'`, `MessageType = 'Alert'`, `MessageText = 'No earnings for
company'`.

**Done when**
- the result is identical computed by `Symbol` and by `SK_SecurityID` — if they
  differ, the window is grouped on the wrong key
- counts match `Audit`'s `FactMarketHistory` entries
- the alert count matches
- the audit's 6 tests report OK
- this phase is timed separately; if it dominates the Historical Load, that is
  the report's performance story

### Phase 10 — Pass the audit at SF=5

**Goal.** The milestone. Everything before it is construction; everything after
is measurement.

**Create.** `tpcdi/phase10_historical.py` — the orchestration that runs phases
5–9 as one timed Historical Load, writes the PCR row through
`sql/di/adapted/tpcdi_validation.sql`, and runs the audit.
`report/phases/phase-10-audit.md`.

**Done when**
- **every one of the audit's tests reports OK** at SF=5
- `DImessages` holds exactly the PCR rows the phase should have written
- the faithful and inner-join audit variants still agree — this is the
  measurement that settles the FULL JOIN equivalence argument in
  `report/phases/phase-03-schema.md` §6.1

**Do not optimise anything before this passes.** A fast wrong answer is worth
nothing, and Part I's experience was that tuning before the harness is
trustworthy produces conclusions that have to be retracted.

### Phase 11 — The incremental updates

**Goal.** Clause 4.6 over `Batch2` then `Batch3`, with the visibility queries
running concurrently from a second session.

**Create.** `tpcdi/phase11_incremental.py`, `sql/di/08_incremental.sql`,
`report/phases/phase-11-incremental.md`.

**Rules that bite.** CDC flags `I`/`U`/`D` in `CDC_DSN` order; an update does
not say *what* changed, so every one is a full comparison. A row may change
several times in one day and the daily grain still allows only one dimension
row. `Prospect.csv` has no change indicators at all — and Clause 4.6.14's trap
is that a row whose `IsCustomer` flag changed but whose values did not must
**not** count as an update. Clause 7.3.7: the visibility queries must run from
a different session than the loader.

**Done when** the audit passes again after each update, SCD-2 invariants hold
*across* batches, and `DImessages` ends with exactly four PCR rows (0, 1, 2, 3).

### Phase 12 — Choose the four scale factors

**Goal.** The course wants a reference size and three smaller ones.

**Create.** `report/phases/phase-12-scale-factors.md`.

**Method.** Generate, load and time at candidate scale factors. Push up until
the Historical Load is the limit on our machine — 16 GiB host, Docker VM 12 GiB
configured, 220 GiB disk. That is 1.0; then roughly 0.1 / 0.2 / 0.5 of it.
Source data is about 93 MiB per unit of `-sf`, so CPU in the transformations
will decide this, not disk.

**Done when** all four complete a full run **with the audit passing**. A scale
factor whose audit fails is not a data point.

### Phase 13 — Measure

**Create.** `tpcdi/phase13_measure.py`, `report/phases/phase-13-results.md`.

**Rules that bite.** Phase timings come from the differences between
`MessageDateAndTime` on the `PCR` rows in `DImessages` (Clause 7.5.1), **not**
from a stopwatch in the driver. Row counts come from `digen_report.txt`
(Clause 6.3), not from counting ourselves.

```
TH  = RH / EH            TIx = RIx / Max(EIx, 1800)
TPC_DI_RPS = Trunc(GeoMean(TH, Min(TI1, TI2)))
```

**Report the raw elapsed times beside the official metric, and say why.** The
incremental batches are about 33k rows against the historical load's 7.8M, so
`Max(E, 1800)` substitutes 1800 every time and that half of the metric measures
the data rather than our system. Without the raw times the numbers say nothing
about anything we did.

**Done when** every scale factor has been run twice, the audit passed on every
run contributing a number, and the two runs are reported separately rather than
averaged.

### Phase 14 — Report and package

**Create.** the PDF report, and a ZIP that reproduces everything.

**Done when** the ZIP, unpacked into a clean directory on a machine that has
never run this, produces a complete result from one command. Test it. Part I's
lesson: tests gate a submission or they are decoration.

## If you are an agent working on this

Pick the next undone phase. Read its section above, then read the report of the
phase before it — the "what this settles for later work" section is written for
you.

Work in this order: write `run()`, get it to load something, write `verify()`,
**break it on purpose and confirm it fails**, then fix until it passes at SF=5
*and* SF=3. Write the report. Commit with a message explaining what you learned.

When you find a defect — in the data, the tooling, or your own earlier work —
write it down rather than quietly fixing it. Four of the most useful paragraphs
in these reports are about mistakes.

If a check fails and you do not understand why, stop and say so. Do not adjust
the check until it passes.
